# 持久化评估

## 结论

当前阶段暂不引入数据库。主分支应继续保持默认 `AI_PROVIDER=local` 可直接运行，优先保证演示流程稳定、示例可复现、自动化测试覆盖核心路径。

## 暂缓原因

- 现有 MVP 已能完成导入文本、生成 YAML、结构化编辑、校验、复制和下载。
- 当前没有账号、权限、团队协作或长期历史查询需求。
- 持久化会引入迁移脚本、错误恢复、数据清理、兼容旧 Schema 和测试数据管理。
- 容器化与数据库服务会增加评委本地复现成本。
- 过早落库会让 PR 范围变大，不符合小粒度 PR 要求。

## 启动条件

满足以下条件后，再启动持久化设计和实现：

- 演示烟测稳定运行，并纳入日常回归或 CI。
- 至少明确一个必须保存的用户流程，例如保存草稿、恢复上次编辑或对比历史版本。
- 明确是否需要账号体系；如果不需要，先按本地单用户项目模型实现。
- 明确 YAML Schema 升级策略。
- 明确主分支在无数据库时是否仍需保留 local 演示模式。

## 建议的第一批实体

```text
projects
script_versions
generation_jobs
```

- `projects`：保存项目标题、原文摘要、创建时间和更新时间。
- `script_versions`：保存每次生成或编辑后的 YAML、Schema 版本、版本序号和来源。
- `generation_jobs`：保存 provider、模型参数、状态、错误信息和耗时，便于复现生成问题。

暂不引入：

- `users`
- `teams`
- `permissions`
- `uploaded_files`
- `async_tasks`

## 首个持久化里程碑

建议拆成多个独立 PR：

1. 新增 SQLite 配置、连接封装和迁移脚本，不接入业务接口。
2. 新增项目保存 API，只保存标题和当前 YAML。
3. 新增版本历史 API，只追加版本，不做复杂 diff。
4. 前端增加保存按钮和历史列表。
5. 为保存和历史查询补充后端测试、前端构建和 E2E 覆盖。

每个 PR 合并后都要保证默认 local 演示仍可运行。

## 风险与缓解

| 风险 | 影响 | 缓解方式 |
| --- | --- | --- |
| 数据库依赖增加复现成本 | 评委无法快速跑通 | 保留无数据库 local 演示 |
| Schema 升级影响旧数据 | 历史 YAML 无法校验 | 每条版本记录保存 `schema_version` |
| 保存原文涉及隐私和版权 | 数据治理范围扩大 | 首批只保存 YAML 和摘要 |
| PR 范围过大 | 难以 review 和回滚 | 按实体和 API 分小 PR |

## 当前排除范围

- 不引入鉴权和团队协作。
- 不引入异步任务队列。
- 不引入完整 Docker Compose 数据库编排。
- 不保存用户导入的原始文件。
- 不实现复杂版本 diff 和冲突合并。
