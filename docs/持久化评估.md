# 持久化评估

## 结论

当前阶段暂不引入数据库。主分支应继续保持默认 `AI_PROVIDER=local` 可直接运行，优先保证演示流程稳定、示例可复现、自动化测试覆盖核心路径。

## 暂缓原因

- 现有 MVP 已能完成导入文本、生成 YAML、编辑、校验、复制、下载和示例回归。
- 持久化会引入项目保存、版本历史、迁移脚本、错误恢复和数据清理等新范围。
- 当前还没有账号、权限、团队协作或长期历史查询需求，过早落库会放大实现和评审成本。

## 启动条件

满足以下条件后，再启动持久化设计和实现：

- 演示烟测稳定运行，并纳入日常回归。
- OpenAI-compatible Provider 的 mock 质量用例稳定通过。
- 至少明确一个必须保存的用户流程，例如保存草稿、对比历史版本或恢复上次编辑。
- 明确是否需要账号体系；如果不需要，先按本地单用户项目模型实现。

## 建议的第一批实体

```text
projects
script_versions
generation_jobs
```

- `projects`：保存标题、原文摘要、创建时间和更新时间。
- `script_versions`：保存每次生成或编辑后的 YAML、Schema 版本、版本序号和来源。
- `generation_jobs`：保存 provider、模型参数、状态、错误信息和耗时，便于复现生成问题。

## 首个持久化 PR 拆分建议

1. 新增 SQLite 配置与迁移脚本，不接入业务接口。
2. 新增项目保存 API，只保存标题和当前 YAML。
3. 新增版本历史 API，只追加版本，不做复杂 diff。
4. 前端增加保存按钮和历史列表。

每个 PR 合并后仍需通过后端 `python -m pytest`、前端 TypeScript 编译和 Vite build。

## 继续排除的范围

- 暂不引入鉴权和团队协作。
- 暂不引入异步任务队列。
- 暂不引入完整 Docker Compose 数据库编排。
- 暂不保存用户导入的原始文件，仅在明确产品需求后再评估文件存储。
